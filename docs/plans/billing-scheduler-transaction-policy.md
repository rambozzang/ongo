# BillingScheduler 트랜잭션 정책 결정

조사일: 2026-08-07
대상: `backend/onGo-application/src/main/kotlin/com/ongo/application/subscription/BillingScheduler.kt`

## 결정

**구독별 격리(`REQUIRES_NEW`)를 채택한다.** 단, 한 구독을 처리하는 동안의 핵심 상태 변경은 하나의 트랜잭션으로 묶는다.

- A 구독의 오류가 B 구독의 정상적인 갱신을 되돌려서는 안 된다.
- A 구독 내부의 `subscription`·`user.planType`·`ai_credits.freeMonthly` 변경은 서로 불일치한 채 커밋되어서는 안 된다.
- 알림 저장은 entitlement의 원천 상태가 아니므로 핵심 상태 트랜잭션의 성공을 막지 않도록 outbox/후속 재시도 또는 별도 best-effort 경계를 검토한다.

## 근거

### 1. 이 작업은 결제 청구가 아니라 상태 조정이다

현재 스케줄러는 외부 결제 API를 호출하지 않는다. 만료·일시정지·미결제·취소 만료·예약 다운그레이드 결과를 DB의 구독/사용자/크레딧 상태에 반영한다(`BillingScheduler.kt:42-163`). 실제 결제 결과는 PortOne/Paddle 웹훅 경로에서 이미 반영된다.

따라서 구독 A의 DB 조정 실패가 구독 B의 결제 승인·청구를 되돌려야 할 교차 사용자 원자성은 없다. 전체 롤백은 B의 이미 올바른 상태까지 지연시키는 효과만 낸다.

### 2. 사용자별 독립성이 도메인 경계다

각 처리 목록은 `sub.userId`를 기준으로 사용자 구독과 플랜을 갱신한다.

- 트라이얼 만료: `BillingScheduler.kt:43-62`
- 일시정지 재개: `:65-80`
- 미결제 3일/7일: `:83-114`
- 취소된 기간 만료: `:119-130`
- 예약 다운그레이드와 크레딧 한도: `:133-163`

한 사용자의 `subscription`과 `user.planType`을 함께 바꾸는 것은 원자적이어야 하지만, 서로 다른 사용자의 변경까지 같은 트랜잭션으로 묶을 이유는 없다.

### 3. 현재 전체 트랜잭션은 실패 격리가 없다

`processBilling` 전체가 `@Transactional`이다(`BillingScheduler.kt:31-33`). 항목별 `catch`는 없으므로 DB 예외가 나면 전체 작업이 실패하고 전체 변경이 롤백된다. 이는 “삼킨 DB 예외” 결함으로 단정할 수는 없지만, 한 행의 데이터 이상·일시적 제약 오류가 모든 사용자의 갱신을 막는 정책이다.

구독별 격리를 적용하면:

- 정상 사용자는 같은 실행에서 계속 처리된다.
- 실패 사용자는 식별 가능한 `userId/subscriptionId`와 함께 재시도 대상으로 남는다.
- 같은 스케줄러의 다음 실행이 실패 사용자만 조건에 다시 걸러 처리할 수 있다.

반대로 전체 롤백을 유지하면 한 건 실패 시 나머지 성공 건도 매일 재처리되며, 실패 목록을 사용자별로 관측하기 어렵다.

## 트랜잭션 경계

### 구독별 원자 단위

다음 변경은 한 사용자의 `REQUIRES_NEW` 트랜잭션 안에서 함께 성공하거나 함께 롤백되어야 한다.

1. `subscriptionRepository.update(...)`
2. 필요한 경우 `userRepository.update(user.copy(planType = ...))`
3. 다운그레이드 시 `creditRepository.update(...freeMonthly...)`

근거는 `BillingScheduler.kt:45-54`, `:97-112`, `:121-129`, `:137-155`다. 구독만 Free인데 사용자 플랜이 유료로 남거나, 플랜은 바뀌었는데 크레딧 월간 한도가 이전 값인 상태는 허용하지 않는다.

### 알림은 보조 효과로 취급

알림 저장은 `BillingScheduler.kt:55-60`, `:73-78`, `:85-90`, `:107-112`, `:156-161`에 섞여 있다. 알림 insert 실패 때문에 이미 유효한 구독 만료/다운그레이드를 롤백하면 entitlement 상태가 알림 인프라에 종속된다.

권장 순서는 다음 중 하나다.

- 핵심 상태 커밋 후 알림을 별도 트랜잭션/outbox로 기록하고 재시도한다.
- 당장 outbox가 없다면 알림 실패를 구조화 로그와 실패 큐로 남기되 핵심 상태 트랜잭션은 유지한다.

알림 중복이 허용되지 않는다면 `userId + transition + effectiveAt` 같은 멱등 키가 필요하다. 현재 중복 알림 정책은 **미확인**이다.

## 구현 시 주의할 데이터 경계

### 조회 목록은 실행 시점에 다시 검증해야 한다

`findPastDue(3)`와 `findPastDue(7)`은 같은 `PAST_DUE` 집합의 서로 다른 cutoff를 조회한다(`SubscriptionJooqRepository.kt:124-133`). 7일 초과 구독은 두 목록에 모두 포함될 수 있다. 또한 `findWithPendingPlanType` 결과는 메모리에서 기간을 한 번 더 필터링한다(`BillingScheduler.kt:133-135`).

따라서 구독별 트랜잭션으로 바꿀 때는 다음을 지킨다.

- 목록에서 읽은 stale 객체를 무조건 덮어쓰지 말고, 트랜잭션 안에서 현재 상태/기간을 재확인한다.
- 같은 실행의 여러 단계에 중복 등장할 수 있는 구독은 상태 전이 조건을 둬 idempotent하게 만든다.
- 이미 FREE/ACTIVE 등 최종 상태인 행을 다시 알림·갱신하지 않는다.
- 다른 인스턴스와의 경합을 막는 행 잠금/조건부 update 정책을 별도로 명시한다.

### 락 커넥션과 구독별 트랜잭션

현재 BillingScheduler는 구형 `tryLock`/`releaseLock`을 사용한다(`BillingScheduler.kt:34`, `:167`). 공유 `withLock`으로 전환하면서 락 커넥션을 잡은 채 `REQUIRES_NEW` 트랜잭션을 열면 DB 커넥션이 최소 2개 필요하다. Hikari 최소 풀 크기 1은 구성 오류로 취급하고, 배포 설정의 최소 풀 요구를 유지해야 한다.

## 대안 비교

| 정책 | 장점 | 결함/비용 | 판단 |
|---|---|---|---|
| 전체 롤백 유지 | 한 실행의 일괄 원자성, 구현 변경 최소 | 한 사용자 오류가 전부 지연; 실패 사용자 식별·부분 재시도 어려움; 매일 전체 재실행 | 채택하지 않음 |
| 구독별 `REQUIRES_NEW` | 사용자 독립성, 정상 구독 진행, 실패 항목 재시도·관측 가능 | 트랜잭션 경계 추출, stale 목록·중복 단계·알림 멱등성 설계 필요 | **채택** |
| 상태/사용자/크레딧까지 각각 별도 커밋 | 한 단계 실패가 다른 단계 차단하지 않음 | 구독-사용자-크레딧 불일치가 돈/권한 오류로 직결 | 채택하지 않음 |

## 필수 검증 시나리오

구현 후 Testcontainers PostgreSQL로 다음을 고정한다.

1. 세 구독 중 두 번째의 `subscriptionRepository.update`가 DB 오류를 내도 첫 번째·세 번째의 구독/사용자 상태가 커밋된다.
2. 한 구독의 사용자 플랜 update가 실패하면 같은 구독의 subscription update와 credit update가 함께 롤백된다.
3. 알림 insert 실패 시 핵심 상태를 유지하는지, 또는 알림까지 원자적으로 묶기로 결정했다면 전체 구독 트랜잭션이 롤백되는지 명시된 정책과 일치한다.
4. `findPastDue(3)`와 `findPastDue(7)`에 동시에 걸리는 구독이 중복 다운그레이드·중복 알림을 만들지 않는다.
5. 두 스케줄러 인스턴스가 같은 구독을 읽어도 한 번만 상태 전이·알림이 적용된다.
6. 락 커넥션을 보유한 상태에서 구독별 트랜잭션이 커넥션 풀 고갈 없이 완료된다.

## 최종 결정

구독 A의 갱신 실패가 구독 B의 갱신을 되돌려야 할 도메인 근거는 없다. **구독별 격리 + 구독 내부 핵심 상태 원자성**이 결제·권한 정합성과 운영 복구성을 함께 만족한다. 전체 롤백은 일괄 스냅샷이 반드시 같아야 한다는 별도 비즈니스 요구가 확인될 때만 재검토한다.
